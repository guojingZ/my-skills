# 阶段 0：业务域画像（写 profile.md）

## 目标

把用户的输入（行业 + 业务域 + 参考文档/方法论/系统清单）整理成一份**建模前的共同约定**，供后续骨架阶段直接引用。这一步不产出任何模型节点，只产出「建什么、多大、按什么口径」。

## 输入

- 用户诉求：`<行业>` + `<业务域>`（可能还给了参考方法论、参考系统、参考文档）
- 文档：`docs/` 下的业务文档（有则读，无则靠领域知识 + 用户补充）

## 输出

写入 `<workdir>/profile.md`，必须包含以下 7 节，每节都要具体到能指导建模，禁止空话。

```markdown
# <行业> · <业务域> 业务域画像

## 1. 业务定位
本业务域在价值链上的位置（上游是谁、下游是谁）、存在的根本目的（一句话）。
2.3 句话说清"没有这个域，企业会缺什么"。

## 2. 端到端主流程
按方法论（如 IPD / ISC / SCOR / LTC / ITR）给出阶段划分，每阶段给：
- 阶段名
- 输入物 → 输出物
- 该阶段的核心决策点（决策点 = 后续规则的种子）
写出 1 条主干流（正常路径）+ 2~3 条典型分支（变更/返工/终止/例外）。

## 3. 能力域清单（后续 capacity 覆盖率的基准）
表格：能力域 ID（CAP-XX）| 能力域名称 | 一句话说明 | 主要承载系统
粒度要求 6~10 项，必须能覆盖主流程的所有阶段，且互不重叠。

## 4. 核心业务对象候选
表格：对象名（中文）| 语义 ID 片段建议（英文大写下划线）| 聚合类型（ENTITY/AGGREGATE_ROOT/REFERENCE）| 一句话职责
- ENTITY：有独立生命周期、被独立引用的业务实体
- AGGREGATE_ROOT：一致性与事务的边界，通常就是单据/主档
- REFERENCE：主数据/参考数据（编码、分类、组织、资源），只被引用不主动流转
数量目标 15~30 个。必须包含主数据对象，否则后续关联会断。

## 5. 关键业务动作候选（行为）
按「对象 → 动作」列出，动词用业务语言（提交评审、冻结基线、拆解工单），
禁止 create/update/delete/get/list 这类 CRUD 词。数量目标 25~50 个。

## 6. 行业硬约束（规则的种子）
列出该行业/该域绕不过去的**判定类**约束（合规、准入、门禁、配额、校验、版本冻结）。
每条给：约束名 + 判定条件 + 违反后果 + 出处（方法论条款 / 法规 / 系统校验）。
数量目标 10~20 条。注意：这里只列，不成文为规则节点。

## 7. 系统与术语口径
- 主流系统能力对照（如 PLM / ERP / MES / CRM / SRM / APS）：每系统承载哪几个能力域
- 术语表：行业黑话 → 本模型统一用词（避免同义异名）
- 明确"不建什么"：本域边界外的对象/流程，防止模型膨胀
```

## 质量要求

- **总量预算前置**：第 4/5/6 节的数量必须落在建模规模预算内（对象 15-30、行为 25-50、规则 10-20），超了就在画像阶段砍，不要留到分片阶段。
- **必须落地到名词**：每一节都要出现具体的业务名词，不能出现"相关数据""各类单据"这类模糊表述。
- **方法论对齐**：第 2 节的主流程必须显式说明对齐了哪个方法论，阶段名尽量沿用方法论原词。
- **边界声明**：第 7 节必须写清本域不建什么，这是后续所有分片避免越界膨胀的唯一依据。

## 交付前的自检

- [ ] 7 节齐全，每节都有具体内容（不是标题占位）
- [ ] 对象候选数 ∈ [15, 30]，行为候选数 ∈ [25, 50]，规则候选数 ∈ [10, 20]
- [ ] 能力域 6~10 项，且覆盖第 2 节所有阶段
- [ ] 第 7 节写了"不建什么"
