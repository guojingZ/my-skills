# 阶段 4：定向修复（读报告 → 改分片 → 重跑）

## 铁律

**只改报告指名的问题。不允许借修复之名重写整个分片。** 重写会引入新错误，且把已经通过校验的内容搞坏。

**永远不要手改 YAML。** YAML 由 `obm.py toyaml` 独占生成，手改会在下一次 toyaml 时被覆盖。

## 报告位点

| 文件 | 何时产生 | 看什么 |
|---|---|---|
| `<workdir>/check-report.json` | `obm.py check <wd> --json` | 片级：字段/ID/枚举/引用 |
| `<workdir>/merged/merge-report.json` | `obm.py merge <wd>` | 合并级：ID 唯一、跨片引用、双向同步 |
| `<workdir>/quality-report.json` | `obm.py quality <wd>` | 全量：预算、反模式、覆盖 |
| `<workdir>/yaml/validation-report.json` | `obm.py render <wd>` | 场景/报表语义警告 |
| `<workdir>/selftest-report.json` | `obm.py selftest <wd>` | HTML 冒烟 |

每条 issue 结构：`{level, code, message, where, ptr, refs}`

- `where`：出问题的分片文件名（如 `m2-00.json`）或阶段名
- `ptr`：精确位点，形如 `m1-00.json#aggregates[3].entities[0].attributes[2]`
- `refs`：涉及的节点 ID 列表（用于 grep 定位）

**修复顺序：先按 `ptr` 用 refs 里的 ID grep 分片定位，改完再重新 check。不要凭 message 猜位置。**

## 错误码速查

### 片级（check）

| code | 含义 | 改法 |
|---|---|---|
| `FIELD_UNKNOWN` | 出现封闭字段集外的键 | 删掉该键，或改用规范键名（最常见：`dictRef`→`dictionaryRef`、`outputParam`→`outputType`、`isPrimary`→`primary`、`items`→`types`） |
| `FIELD_REQUIRED` | 缺必填字段 | 补上。注意事件用 `eventId`/`eventName`，其他用 `id`/`name` |
| `ID_PREFIX` | ID 前缀不对 | 按规范改前缀。报表 `QR-`/`RPT-` 均可 |
| `ID_DUP` | 片内重复 | 保留一个，另一个改名（若语义不同）或删除（若重复） |
| `ENUM` | 枚举值非法 | 按 spec `enums` 里的允许值改。**最常见的三个坑**：`aggregateType` 只能 `AGGREGATE_ROOT`；`associationType` 只能 `REFERENCE`/`DEPENDENCY`；`cardinality` 不能写 `1:N`，要写 `ONE_TO_MANY`（实体 `cardinality` 也是这套） |
| `ATTR_TYPE` | 属性类型不在规范 13 值内 | 常见错误：用了 `Text`（改 `String`）、外键用了 `String`（改 `AggregateRootRef`）、字典用了 `Enum`（改 `DictionaryRef`） |
| `ATTR_REF` | `AggregateRootRef` 缺 `targetAggregate` | 补上目标聚合 ID |
| `ATTR_DICT` | `DictionaryRef` 缺 `dictionaryRef` | 补上字典 ID |
| `ATTR_ENUM` / `ATTR_ENUM_DUP` | `Enum` 缺 `enumValues` / 枚举值重复 | 补值或去重 |
| `REF_UNKNOWN` | 引用了不存在的 ID | 二选一：①改成骨架里真实存在的 ID；②回骨架补这个 ID 再重跑全部引用方。**优先选①** |
| `SUB_REQUIRED` / `SUB_UNKNOWN` | 子结构缺键 / 多键 | 按对应 sub 的 required/allowed 改 |
| `FIELD_OBJ` / `FIELD_MISSING` | 字段类型错 / 字段级引用落空 | 按 message 指出的期望类型改。规则 `inputParams.sourceField` 与事件 `payload.sourceField` 会校验 `OBJ-XXX.attrName` 必须真实存在 |

### 合并级（merge）

| code | 含义 | 改法 |
|---|---|---|
| `ID_DUP`（跨片） | 同一 ID 在两个分片重复定义 | 删掉后出现的那一份 |
| `REF_UNRESOLVED` | 合并后引用仍落不了地 | 该类节点确实没建 → 要么建，要么把引用改成已有 ID |
| `BIDIRECT_FIX` | 双向引用被自动同步（info） | **不用改**，但下一次要自己写对，别依赖自动补 |
| `COLLECTION_UNKNOWN` | 分片里出现该模型不允许的集合 | 把内容搬到正确的模型分片 |

### 质量级（quality）

| code | 含义 | 改法 |
|---|---|---|
| `BUDGET_HARD` | 超硬上限 | 必须删减，合并同义节点 |
| `BUDGET`（超建议上限） | 略多 | 优先合并语义重叠的节点，不要简单删 |
| `BUDGET_LOW`（低于下限） | 模型过度简化 | 补节点。这是最该重视的一类，说明建模没到位 |
| `AP_CRUD` | CRUD 命名占比 >40% | 把 `createXxx` 改成业务动词（`发起Xxx`/`登记Xxx`/`提报Xxx`），或合并进上层业务动作 |
| `AP_THIN`（info） | COMMAND 无规则无事件 | 补 `producedEvents`（首选）或 `appliedRules`；确实纯查询的改 `behaviorType=QUERY` |
| `AP_SCN_SHORT` | 场景 <5 步 | 补步骤，把真实分支展开 |
| `AP_SCN_NARROW` | 场景跨 <3 对象 | 把流程延长到下一个对象（如"发布"延到"上市"） |
| `AP_RPT_TRIVIAL` | 报表单源无聚合 | 加关联对象（走 `joins`）或加聚合列 |
| `COV_OBJ_NO_BEHAVIOR` | 对象无行为 | 主数据对象（REFERENCE）可注释豁免；业务对象必须补行为 |
| `COV_RULE_UNUSED` | 规则没人用 | 挂到某个行为的 `appliedRules`（若确属该行为的判定），否则删规则 |
| `COV_EVENT_NO_SUB` | 事件无订阅 | 补 `subscribers`；对外广播的写 `SYSTEM` 订阅者 |
| `COV_RPT_NO_BEHAVIOR` | 报表无行为 | 在 m2 补一个 QUERY 行为，把报表挂上去 |
| `COV_DICT_UNUSED` | 字典没被属性引用 | 把相关属性的 `dictionaryRef` 指向它，或删字典 |
| `COV_CAP`（quality，需 `_evidence.json`） | 能力域没绑节点 | 给相关节点加 `_cap` 旁挂键 |
| `SMOKE_*` | HTML 冒烟失败 | 重新 render；`SMOKE_SIZE` 多半是 assets 缺失 |

### 场景/报表语义（render 前的 validation-report）

**注意：这些是 `render` 阶段才暴露的，`check` 抓不到。所以写完 m2/m4/m7 就要预判它们。**

| code | 含义 | 改法 |
|---|---|---|
| `M2_QUERY_POST` | QUERY 行为带了 `postconditions` | 清空 QUERY 的 `postconditions`（查询不改变状态） |
| `M4_CYCLE` | 场景步骤链路成环（如 `S01->S02->S08->S01`） | **删掉回退边**。分支失败路径改成终止步（`nextSteps: []`），`condition` 写"退回 X，本场景终止"。完整返工回路另建场景 |
| `M4_TARGET_INDIRECT` | 目标对象没在步骤里出现 | 找一个产出该对象的步骤（其行为的 `ownerEntity` 就是它），或把该对象挂到某步行为上 |
| `M4_TRIGGER_EXTERNAL` | 触发事件不由本场景产生（warning，可接受） | 说明它是上游场景的外部前置；若该事件其实应由本场景产生，加一步 `EVENT_EMIT` |
| `ENUM`（viewer 报的） | 实体 `cardinality` 写成 `1:N` | 改 `ONE_TO_MANY`；实体基数与关联基数共用同一套枚举 |
| `COVERAGE_OBJECT` | 对象无直连行为 | 主数据可接受，保留 warning |

## 修复循环

```
1) obm.py check <wd> --json        # 必须先到 0 error 才往下走
2) obm.py merge <wd>               # 0 error
3) obm.py quality <wd>             # 看 BUDGET_LOW / AP_* / COV_*
4) 按上表逐条改 _parts/*.json
5) 回到 1)，直到 quality 得分 ≥ 80 且无 error
```

一轮最多改 10 条 issue。改完立刻重跑，不要攒着改完 50 条再验证——攒着改必然互相打架。

## 旁挂键（不进入 YAML，但影响质量评分）

节点上可以加下划线开头的键，`obm.py toyaml` 会剥离，`merge` 会收进 `merged/_evidence.json`：

- `_cap`：字符串或数组，能力域 ID（`CAP-XX`），用于 `COV_CAP` 覆盖率
- `_evidence`：文档证据锚点，如 `"§3.2 Charter评审门禁"`，用于 `EVIDENCE` 统计

建议在行为/规则/事件节点上都加 `_cap` 和 `_evidence`，这是"模型可追溯"的唯一实现方式，也是质量分的主要抓手。

## 什么时候该停下问人

- 报告指出的问题是**骨架层面**的（比如某个能力域完全没排节点）→ 停下来问：是补骨架还是承认该能力域不建
- `BUDGET_LOW` 连续两轮补不上 → 说明业务域本身信息量不足，问用户要不要扩大范围
- 用户给的文档与领域常识冲突 → 以文档为准，但把冲突点列出来请用户确认
